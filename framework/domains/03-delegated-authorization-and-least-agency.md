# Domain 3: Delegated Authorization & Least Agency

**Objective:** Give each agent only the [autonomy](../../guides/tiering.md#autonomy-levels), tools, scopes and spend its task requires, enforce those limits outside the model, and keep people in control of high-risk actions and of the off-switch.

## Why it matters

Most damaging agent incidents need no exotic exploit. The agent simply used authority it already held. In July 2025 Replit's coding agent deleted a production database during a declared code freeze. In May 2025 a single public GitHub issue steered an agent holding a broad access token into copying private repository data into a public pull request. Prompt injection and model error cannot be ruled out inside the model, so the dependable limits sit outside it. Those limits are: [autonomy](../../guides/tiering.md#autonomy-levels) granted per action class and earned with evidence; tools and scopes enforced by deterministic policy; no session that combines untrusted input, sensitive access and an unconstrained outbound channel; human approval for consequential actions; bounded spend; and a tested way to halt an agent.

**Key risks addressed**

- [OWASP Top 10 for LLM Applications 2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/README.md): LLM01:2026 Prompt Injection; LLM03:2026 Excessive Agency; LLM06:2026 Unbounded Consumption
- [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/): ASI01 Agent Goal Hijack; ASI02 Tool Misuse & Exploitation; ASI03 Identity & Privilege Abuse; ASI08 Cascading Failures; ASI09 Human-Agent Trust Exploitation; ASI10 Rogue Agents
- [MITRE ATLAS](https://github.com/mitre-atlas/atlas-data/releases/tag/v2026.09) (release 2026.09): AML.T0053 AI Agent Tool Invocation; AML.T0086 Exfiltration via AI Agent Tool Invocation; AML.T0101 Data Destruction via AI Agent Tool Invocation; AML.T0081 Modify AI Agent Configuration; AML.T0034 Cost Harvesting; AML.T0024.002 Extract AI Model

## Autonomy levels

[BAL-3.1](../../controls/control-catalog.md#bal-3-1) records an [autonomy level](../../guides/tiering.md#autonomy-levels) for each action class an agent can perform. It does not assign one level per agent. Configuration outside the model enforces each level, and a level goes up only through a promotion gate. The highest level across an asset's action classes feeds its risk rating ([BAL-1.5](../../controls/control-catalog.md#bal-1-5)). Any class at [A3](../../guides/tiering.md#a3) or above makes the asset at least High, and any class at [A4](../../guides/tiering.md#a4) makes it Critical.

| Level | Name | What the agent can do | Notes |
|---|---|---|---|
| [A0](../../guides/tiering.md#a0) | Read-only | Retrieves, reads and summarizes. It has no tools that change state. | Not risk-free. Rendered links and images, URL fetches and memory writes can still carry data out, so [BAL-3.5](../../controls/control-catalog.md#bal-3-5) and [BAL-6.3](../../controls/control-catalog.md#bal-6-3) apply whenever it processes untrusted content. EchoLeak (June 2025) took data out of an enterprise assistant through an auto-fetched image. |
| [A1](../../guides/tiering.md#a1) | Suggest | Proposes content or actions. A human carries them out through a separate, normal channel. | One-click execution of a proposed tool call is [A2](../../guides/tiering.md#a2), not [A1](../../guides/tiering.md#a1). |
| [A2](../../guides/tiering.md#a2) | Act with approval | Executes an action after a human approves that specific action, as displayed by the enforcement point ([BAL-3.6](../../controls/control-catalog.md#bal-3-6)). | Turning on auto-approve for an action class moves that class to [A3](../../guides/tiering.md#a3), which needs a promotion gate. |
| [A3](../../guides/tiering.md#a3) | Bounded autonomous | Acts without per-action approval inside a declared envelope of tools, scopes, egress, rate, budget and time. | [BAL-3.6](../../controls/control-catalog.md#bal-3-6) high-risk classes need per-action approval unless an authorized person approves specified actions and targets within recorded limits and an expiry date at the promotion gate. Limits are enforced outside the model; other required reviews still apply. Makes the asset at least High. |
| [A4](../../guides/tiering.md#a4) | [High autonomy](../../guides/tiering.md#autonomy-levels) | Pursues self-initiated or open-ended goals. It decides what to do, or when to act, without a task defined by a human. | [A4](../../guides/tiering.md#a4) authorization only, under the restrictions below. ### One level per action class

An action class is a kind of action, such as reading CRM records, drafting a reply, sending external email or merging to a protected branch. Classes come from the capability classes in [BAL-3.3](../../controls/control-catalog.md#bal-3-3) and the high-risk classes in [BAL-3.6](../../controls/control-catalog.md#bal-3-6). A typical assistant might perform ordinary task-scoped reads at [A0](../../guides/tiering.md#a0), draft at [A1](../../guides/tiering.md#a1) and send external email at [A2](../../guides/tiering.md#a2). A single level per agent would either overstate or understate its authority. Report the highest level as the agent's headline level.

### Initiation mode

Record whether each agent is human-initiated or event-triggered. A human-initiated agent starts each task because a person asks it to. An event-triggered agent is started by a schedule, webhook, inbound message or another agent. Initiation mode does not set the level: an agent that wakes on an inbound email and only drafts a reply is [A1](../../guides/tiering.md#a1) for drafting. It does change exposure. When the triggering event can carry content from outside the organization or from other principals (inbound email, tickets, pull requests, web forms, other agents), the asset is tagged UNTRUSTED and [BAL-3.5](../../controls/control-catalog.md#bal-3-5) applies. Event-triggered coding agents in CI/CD also fall under [BAL-5.23](../../controls/control-catalog.md#bal-5-23). A scheduled task limited to ordinary reads remains [A0](../../guides/tiering.md#a0). Choosing its own goals or starting work without a human-defined task remains subject to [A4](../../guides/tiering.md#a4). Secret retrieval, privileged credential use and outbound actions keep their existing approval requirements.

### Promotion gate

To elevate an action class to a higher [autonomy level](../../guides/tiering.md#autonomy-levels), a documented promotion decision is required, as is the case for deploying a new agent featuring any action class exceeding [A2](../../guides/tiering.md#a2); in such instances, the operational record originates from a pilot located at [A2](../../guides/tiering.md#a2) or lower. The record encompasses:

1. **Target-level controls, tested.** Re-assess the risk rating ([BAL-1.5](../../controls/control-catalog.md#bal-1-5)) at the target level first. Promotion to [A3](../../guides/tiering.md#a3) makes the asset at least High. That brings in [T2](../../guides/tiering.md#t2) controls such as rate limits ([BAL-3.9](../../controls/control-catalog.md#bal-3-9)), budgets ([BAL-3.10](../../controls/control-catalog.md#bal-3-10)) and the automatic circuit breaker ([BAL-3.11](../../controls/control-catalog.md#bal-3-11)). Attach test results for each control the target level requires.
2. **Operating record at a lower level.** Cover a defined minimum period (for example 30 days) and include action volume, approval rejections and edits, policy blocks, errors and incidents. A high rejection rate shows the agent is not ready. A near-zero rejection rate over meaningful volume suggests the approvals add little (see [BAL-3.12](../../controls/control-catalog.md#bal-3-12) for High and Critical assets).
3. **Updated design records.** These are the threat model ([BAL-5.1](../../controls/control-catalog.md#bal-5-1), for assets the organization builds) and the [BAL-3.5](../../controls/control-catalog.md#bal-3-5) A/B/C profile.
4. **The envelope.** For [A3](../../guides/tiering.md#a3), record the tools, scopes, egress, rate, budget and time limits. Also record each pre-authorized [BAL-3.6](../../controls/control-catalog.md#bal-3-6) action, its targets, limits and expiry (for example refunds to specified recipients within per-refund and daily limits until a set date). Enforce the limits outside the model, block actions after expiry, and retain other required human reviews. For the [BAL-3.13](../../controls/control-catalog.md#bal-3-13) classes, use its separate approval channel for the original approval and any changes or renewals.
5. **Sign-off** by the asset owner ([BAL-1.4](../../controls/control-catalog.md#bal-1-4)) and by security, under the decision rights in [BAL-1.2](../../controls/control-catalog.md#bal-1-2).

Demotion needs no gate. The owner, an approver or security can lower a level at any time, for example after an incident, an anomaly or a failed test. Agents cannot promote themselves: their identities have no permission to change their own level, tools, scopes or approval settings, or to create agents, triggers or schedules at a higher level than their own ([BAL-3.1](../../controls/control-catalog.md#bal-3-1), and [BAL-6.16](../../controls/control-catalog.md#bal-6-16) for coding agents on endpoints). Narrowing the tools, scopes and budget a sub-agent receives is [BAL-2.12](../../controls/control-catalog.md#bal-2-12).

### [A4](../../guides/tiering.md#a4) restrictions

[A4](../../guides/tiering.md#a4) is permitted only when all of the following hold:

- An executive risk owner approves an [A4](../../guides/tiering.md#a4) authorization in the [BAL-1.13](../../controls/control-catalog.md#bal-1-13) register for at most 6 months. Link it to the [BAL-3.1](../../controls/control-catalog.md#bal-3-1) assessment and approved action classes. Every renewal needs a new promotion gate; operation stops at expiry.
- Every [T2](../../guides/tiering.md#t2) and [T3](../../guides/tiering.md#t3) control applicable to the asset is implemented, and the asset's kill switch ([BAL-3.7](../../controls/control-catalog.md#bal-3-7)) has been tested.
- The asset satisfies [BAL-3.5](../../controls/control-catalog.md#bal-3-5).
- The asset cannot reach restricted or regulated data, does not make or materially support consequential decisions about individuals, and performs no irreversible financial actions.

## The Rule of Two

[BAL-3.5](../../controls/control-catalog.md#bal-3-5) adopts the [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/), published by Meta on 31 October 2025. It builds on Simon Willison's "[lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)" (June 2025). Within one session, an agent should hold at most two of these three properties:

- **[A] Untrusted input:** content an attacker can influence.
- **[B] Sensitive access:** private data or sensitive systems.
- **[C] Outbound or state-changing capability:** anything that changes state or sends data across the trust boundary.

With all three, a single successful prompt injection can read private data and send it out, or take a damaging action. No model-level defense reliably prevents injection (UK NCSC, December 2025; Nasr et al., "The Attacker Moves Second", October 2025). The rule therefore removes or constrains the combination instead of relying on detection. [MITRE ATLAS](https://github.com/mitre-atlas/atlas-data/releases/tag/v2026.09) recommends a related approach in AML.M0030, which restricts automatic tool invocation once untrusted data is in context.

Ballast makes three points explicit:

1. **Insiders' content counts.** (A) includes shared documents, tickets, chat messages and other agents' output written inside the organization, not only external content.
2. **Rendering counts as acting.** (C) includes rendering a link or image, fetching a URL and writing to memory. EchoLeak (June 2025) carried data out through an auto-fetched image. ForcedLeak (September 2025) carried data out through an allowlisted domain that had expired and could be re-registered.
3. **When all three are needed,** each (C) action is handled in one of three ways. It passes a deterministic allowlist the model cannot change, or a person approves it individually ([BAL-3.6](../../controls/control-catalog.md#bal-3-6)), or the workflow is split so that the part reading untrusted content has no sensitive access or no outbound channel. A common split uses a quarantined model that returns only structured values to a privileged planner, so the planner never sees the raw text (Beurer-Kellner et al., 2025). Pre-authorizing a class at [A3](../../guides/tiering.md#a3) does not by itself satisfy the rule; its limits must work as a deterministic allowlist.

| Example | A | B | C | How [BAL-3.5](../../controls/control-catalog.md#bal-3-5) is met |
|---|---|---|---|---|
| Email assistant that summarizes inbound mail and can send replies | Yes | Yes (mailbox) | Yes (sending; rendered images) | Each external send is approved individually ([BAL-3.6](../../controls/control-catalog.md#bal-3-6)). Rendering is limited to allowlisted origins ([BAL-6.3](../../controls/control-catalog.md#bal-6-3)). |
| CI agent that triages public issues | Yes | Split away | Yes (labels and comments) | Split. The triage job reads issue text but holds no secrets, only a token that can label and comment. | Policy assistant grounded on a curated, owner-maintained corpus, with no tools | No, if writers are limited ([BAL-4.9](../../controls/control-catalog.md#bal-4-9)) | Yes | Rendering only | Holds at most two, so it is not tagged UNTRUSTED. | Security operations, IT helpdesk or identity agent | Yes (alerts, tickets and chats are written by attackers) | Yes (privileged) | Yes (closes alerts, resets credentials) | A+B+C by design. Credential and account-recovery actions are approved individually ([BAL-3.6](../../controls/control-catalog.md#bal-3-6)). |---|---|---|
| [BAL-3.1](../../controls/control-catalog.md#bal-3-1) | [Autonomy level](../../guides/tiering.md#autonomy-levels) enforcement and promotion | Action classes come from [BAL-3.3](../../controls/control-catalog.md#bal-3-3) and [BAL-3.6](../../controls/control-catalog.md#bal-3-6); the highest level feeds [BAL-1.5](../../controls/control-catalog.md#bal-1-5). Suggested default: at least 30 days at the lower level, with action volume, approval rejections and edits, and incidents attached; for a new agent, a production pilot at [A2](../../guides/tiering.md#a2) qualifies. Demotion needs no gate. Narrowing sub-agents' tools, scopes and budget is [BAL-2.12](../../controls/control-catalog.md#bal-2-12). Prior art: [Agentic Trust Framework](https://cloudsecurityalliance.org/blog/2026/02/02/the-agentic-trust-framework-zero-trust-governance-for-ai-agents) (J. Woodruff, CSA blog, Feb 2026). |
| [BAL-3.2](../../controls/control-catalog.md#bal-3-2) | Deterministic tool policy enforcement | Tool names are unique only within one MCP server, and the MCP specification treats annotations from untrusted servers as untrusted, so key the allowlist on server identity. The enforcement point can be agent-framework middleware, an MCP gateway or proxy, or platform policy hooks (see the [OWASP Agent Control Standard](https://genai-security-project.github.io/agent-control-standard/)). Example constraints: external recipients limited to approved domains, writes limited to the task workspace, per-transaction amount caps. [BAL-6.18](../../controls/control-catalog.md#bal-6-18) adds non-bypassability. |
| [BAL-3.3](../../controls/control-catalog.md#bal-3-3) | Capability-classified tool policy | Classify by what a tool can do, not by its name or description; one tool can hold several classes. Adding a sensitive-data-read class lets the [BAL-3.5](../../controls/control-catalog.md#bal-3-5) profile be derived from the classification. Re-classify when [BAL-5.17](../../controls/control-catalog.md#bal-5-17) detects a definition change. MCP sampling lets a server request completions from the client's model, which gives the server a path to inject instructions. |
| [BAL-3.4](../../controls/control-catalog.md#bal-3-4) | Audience-bound minimal scopes | Bind tokens to one resource, for example with OAuth resource indicators ([RFC 8707](https://www.rfc-editor.org/info/rfc8707/)), which the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) uses. Prefer fine-grained, per-resource tokens to broad personal access tokens: in the May 2025 GitHub MCP case, a token covering all of a user's repositories let an injected public issue expose private ones. Organization-wide application permissions (all mailboxes, all sites) count as wildcard scopes. |
| [BAL-3.5](../../controls/control-catalog.md#bal-3-5) | Untrusted-input capability separation | Named after Meta's [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/) (Oct 2025), which builds on Simon Willison's [lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) (Jun 2025); see ATLAS AML.M0030. Security operations, IT helpdesk and identity agents are A+B+C by default, because alerts, tickets and chats are attacker-authored. An asset holding all three is rated High ([BAL-1.5](../../controls/control-catalog.md#bal-1-5)), which brings in vendor evidence under [BAL-8.6](../../controls/control-catalog.md#bal-8-6). Delimiting or detecting injected text does not break the combination. |
| [BAL-3.6](../../controls/control-catalog.md#bal-3-6) | Human approval of high-risk actions | A model-written summary may accompany the parameters but never replaces them. Binding approvals to a hash of the parameters voids them on any change. A dependency already in the lockfile and resolved through the governed registry ([BAL-5.20](../../controls/control-catalog.md#bal-5-20)) counts as approved. Example [A3](../../guides/tiering.md#a3) pre-authorization: refunds only to specified recipients, within per-refund and daily limits, until a set date. [BAL-3.2](../../controls/control-catalog.md#bal-3-2) enforces those limits outside the model; [BAL-3.13](../../controls/control-catalog.md#bal-3-13) protects the approval and any changes or renewals. Independent review of agent-authored merges under [BAL-5.22](../../controls/control-catalog.md#bal-5-22) still applies. Motivating cases: Replit database deletion (Jul 2025), PixelLeak (Sep 2026). |
| [BAL-3.7](../../controls/control-catalog.md#bal-3-7) | Agent kill switch | Suggested time objective: 15 minutes from decision to full effect. Access tokens that cannot be revoked need lifetimes shorter than the objective ([BAL-2.4](../../controls/control-catalog.md#bal-2-4)). Define safe states per transaction type, for example roll back, complete or hold for review. Test on a representative agent with a scheduled task and a sub-agent. Automatic tripping is [BAL-3.11](../../controls/control-catalog.md#bal-3-11). |
| [BAL-3.8](../../controls/control-catalog.md#bal-3-8) | AI spend ceilings and usage anomaly alerting | LLMjacking uses stolen keys or cloud credentials to run models at the victim's expense; Unit 42 (Sep 2026) reported a victim's own AI endpoints turned into attack infrastructure. Disable model access in cloud accounts and regions with no approved use. Set ceilings with headroom and an override path; automatic suspension is optional, to avoid self-inflicted denial of service on customer-facing endpoints. |
| [BAL-3.9](../../controls/control-catalog.md#bal-3-9) | Rate limits and exposed-endpoint quotas | Combine short-term rate, burst and concurrency limits with longer-term quotas (ATLAS AML.M0004). Extraction and scraping signals include many near-duplicate queries, systematic coverage of an input space, unusual volume per key, and traffic spread across accounts to stay under limits. Per-agent limits work independently of budgets ([BAL-3.10](../../controls/control-catalog.md#bal-3-10)) and the kill switch. |
| [BAL-3.10](../../controls/control-catalog.md#bal-3-10) | Per-agent and per-workflow budgets | Apply caps across the whole workflow, because one request can start many model calls and tool actions (ATLAS AML.M0036). Suggested alert thresholds: 50% and 80% of each cap. Program-level ceilings in [BAL-3.8](../../controls/control-catalog.md#bal-3-8) protect the provider account; these budgets contain a single runaway agent or workflow. |
| [BAL-3.11](../../controls/control-catalog.md#bal-3-11) | Automatic circuit breaker | Example trip conditions: an execution limit reached repeatedly within a window, a burst of destructive or egress actions, or an anomaly score above threshold. Test by injecting a synthetic threshold breach and confirming the halt completes within the [BAL-3.7](../../controls/control-catalog.md#bal-3-7) time objective. Tripping uses the same halt as the manual kill switch, so test results for one support the other. |
| [BAL-3.12](../../controls/control-catalog.md#bal-3-12) | Approval effectiveness monitoring | Rubber-stamp signals: approval rates near 100% over meaningful volume, median decision times of a few seconds, or one approver handling a large share of a class. Anthropic reported that users approve 93% of Claude Code permission prompts (Mar 2026). Cutting prompt volume through sandboxing or deterministic policy often improves safety more than adding prompts. Addresses [OWASP Agentic AI Threats and Mitigations](https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/) T10, Overwhelming the Human in the Loop. |
| [BAL-3.13](../../controls/control-catalog.md#bal-3-13) | Out-of-band approval for critical actions | Example: [OpenID Connect CIBA](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html) with rich authorization requests ([RFC 9396](https://www.rfc-editor.org/info/rfc9396/)), deployed following [RFC 10027](https://www.rfc-editor.org/rfc/rfc10027.html) (BCP 247) on cross-device flows. The channel can be an authenticator push or a separate payments approval system, but not the chat, IDE or ticket session the agent operates in. Phishing-resistant authentication for approvers is recommended. An asset with none of these classes meets the control by recording that fact. |

## Evidence examples

Examples of evidence an assessor can request. They are illustrative; any evidence that demonstrates the outcome is acceptable.

| ID | Control | Evidence examples |
|---|---|---|
| [BAL-3.1](../../controls/control-catalog.md#bal-3-1) | [Autonomy level](../../guides/tiering.md#autonomy-levels) enforcement and promotion | Asset register entries showing initiation mode and [autonomy level](../../guides/tiering.md#autonomy-levels) per action class; promotion gate records with test results, operating-record data and owner and security sign-off, and any approved [A3](../../guides/tiering.md#a3) actions, targets, limits and expiry; [A4](../../guides/tiering.md#a4) authorization reference linked to its approved action classes and gate record; configuration showing the agent identity cannot modify its own tools, scopes or approval settings or create higher-level agents or schedules. |
| [BAL-3.2](../../controls/control-catalog.md#bal-3-2) | Deterministic tool policy enforcement | Enforcement-point allowlist keyed by server identity, tool name and definition fingerprint; test results showing denial of an unlisted tool, a same-named tool from another server and an out-of-constraint recipient; sample decision records in the action log. |
| [BAL-3.3](../../controls/control-catalog.md#bal-3-3) | Capability-classified tool policy | Tool classification register listing each tool, its classes, who classified it and when; per-class policy configuration; test results showing that an unclassified tool and an MCP sampling request are rejected. |
| [BAL-3.4](../../controls/control-catalog.md#bal-3-4) | Audience-bound minimal scopes | Scope-to-tool mapping for each agent; token and grant inventory showing audience and scopes per agent identity; approved exceptions for wildcard or administrative scopes and log entries for recent scope elevations. |
| [BAL-3.5](../../controls/control-catalog.md#bal-3-5) | Untrusted-input capability separation | A/B/C profile recorded with the asset's risk rating; design record showing, for each (C) action in a session holding all three, the allowlist, approval or split applied; indirect-injection test results, or vendor configuration review, for the asset. |
| [BAL-3.6](../../controls/control-catalog.md#bal-3-6) | Human approval of high-risk actions | Approval policy listing high-risk action classes and authorized approvers; approval prompts showing full parameters with hidden characters revealed; tests rejecting reused, altered and self-issued per-action approvals. Where [A3](../../guides/tiering.md#a3) actions are pre-authorized, the promotion gate records approved actions, targets, limits and expiry, with tests showing actions outside the limits or after expiry are blocked and other required reviews remain enforced. |
| [BAL-3.7](../../controls/control-catalog.md#bal-3-7) | Agent kill switch | Kill-switch runbook naming authorized operators and the time objective; latest test record showing elapsed time, revoked credentials, canceled scheduled tasks and halted sub-agents; per-agent record of created triggers, schedules and sub-agents. |
| [BAL-3.8](../../controls/control-catalog.md#bal-3-8) | AI spend ceilings and usage anomaly alerting | Ceiling settings for each provider account, project, key and inference endpoint, reconciled to the [BAL-1.8](../../controls/control-catalog.md#bal-1-8) inventory; alert rules and a recent alert with its handling; record of a timed key-revocation exercise. |
| [BAL-3.9](../../controls/control-catalog.md#bal-3-9) | Rate limits and exposed-endpoint quotas | Rate-limit and quota configuration per agent identity and per external consumer; detection rule for extraction or scraping patterns; record of a triggered limit or alert and how it was handled. |
| [BAL-3.10](../../controls/control-catalog.md#bal-3-10) | Per-agent and per-workflow budgets | Budget configuration per agent and workflow showing caps and alert thresholds; log of a budget alert and an automatic suspension; approval record for a cap reset or increase. |
| [BAL-3.11](../../controls/control-catalog.md#bal-3-11) | Automatic circuit breaker | Circuit-breaker rules linking each threshold to the halt mechanism; quarterly trip-test records showing time to halt; alert and release records for an actual or test trip. |
| [BAL-3.12](../../controls/control-catalog.md#bal-3-12) | Approval effectiveness monitoring | Approval metrics per approver and action class for the last period; documented rubber-stamp thresholds; records of reviews, policy changes or reassignments those thresholds triggered. |
| [BAL-3.13](../../controls/control-catalog.md#bal-3-13) | Out-of-band approval for critical actions | Configuration listing action classes using the separate approval channel; sample approvals showing transaction details or the approved [A3](../../guides/tiering.md#a3) actions, targets, limits and expiry; access tests showing the agent cannot read or write the channel; tests rejecting expired or out-of-limit actions and changes or renewals without fresh approval. |
